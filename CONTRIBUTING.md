# Contributing to Build with LumynQ

Thank you for helping make emotionally intelligent product development more rigorous, useful, and accessible.

## Start with the human consequence

Good contributions should improve how the Skill helps people act, understand, recover, decide, or retain meaningful choice. Avoid changes that reduce emotional intelligence to tone, forced positivity, or generic empathy language.

## Before proposing a change

1. Search existing issues and pull requests.
2. Describe the product moment or workflow that exposed the need.
3. Separate what you observed live, in code, or in a plan from what you inferred.
4. Explain the human consequence.
5. Include a concrete acceptance test when behavior changes.

## Pull requests

- Keep changes focused.
- Preserve the boundary between the public Skill, LumynQ Core, and customer-specific Domain Packs.
- Do not add proprietary prompts, customer data, confidential Domain Packs, or undocumented Core behavior.
- Keep the installable Skill concise; place public documentation outside `skills/build-with-lumynq/`.
- Update the plugin version when the public behavior or package changes.
- Validate both the Skill and plugin before requesting review.

## Finding format

For reviews or behavioral corrections, use:

```text
Moment:
Evidence class:
Evidence:
Human consequence:
Severity:
Required change:
Acceptance test:
```

## Respectful participation

Discuss the work directly and generously. Critique product behavior and evidence; do not diagnose, shame, or speculate about the people who built or use it.
